# ODPM at a Glance

**Ontology-Driven Practice Model (ODPM)**

> ODPM is the Ontology-Driven Practice Model.

It is the base ontology-driven framework for turning intent into shared ontology, using that ontology to reach Decision Readiness, executing lightly against it, and updating it as reality pushes back.

ODPM does not replace PMBOK, Agile, Scrum, Kanban, SAFe, or other methodologies.
Those methodologies manage execution.
ODPM clarifies the shared model of reality those methodologies execute against.

ODPM began as Ontology-Driven Project Management. As the framework matured beyond product and project management, the same acronym now names the broader Ontology-Driven Practice Model.

## The Two Layers

### Base Ontology Layer

What ontology is, and how teams model the world:

- Entities
- Relationships
- Actions
- States
- Rules

### Lightweight Execution Layer

How teams use ontology in practice:

```text
source artifact
→ ontology
→ open questions
→ Decision Readiness
→ execution
→ feedback
```

## The Building Blocks of an Ontology

An ontology is built from five fundamental elements.

### Entities

The things that exist.

Examples:

- User
- Vehicle
- Campaign
- OTA Update

Ask:

> What exists?

---

### Relationships

How entities are connected.

Examples:

- User owns Vehicle
- Vehicle receives OTA Update
- Campaign targets Vehicle

Ask:

> How are they related?

---

### Actions

The named, legitimate ways an entity moves from one state to another.

Examples:

- Install (Downloading → Installing)
- Rollback (Install Failed → Rollback Required)
- Offer Update (Not Eligible → Available)

Ask:

> What is this transition called?
>
> Who is allowed to trigger it?

---

### States

The current reality of an entity.

Examples:

Available → Downloading → Installing → Completed

Ask:

> What condition can they be in?
>
> What is possible next?

---

### Rules

The constraints that govern the world.

Examples:

- Only Owners can start an OTA Update.
- Scheduling must be within 24 hours.

Ask:

> What must always hold?

## Core Principles

- A shared ontology before execution.
- Questions over assumptions.
- Clarity over complexity.
- Principles over procedures.
- Alignment over individual brilliance.
- Decision Readiness, not complete understanding.
- Every artifact is a snapshot. Ontology evolves.

## Glossary

**Ontology**

The team's shared model of the world.

---

**Entity**

Something that exists in the world the team is building.

---

**Action**

A named, legitimate way to move an entity from one state to another.

---

**Chase Understanding**

Using questions to discover reality together.

---

**Decision Readiness**

The team's current ontology is sufficient to take the next responsible action.

---

**Snapshot**

The team's current best expression of the ontology at a point in time.

---

**Source Artifact**

A PRD, brief, charter, mandate, or other artifact containing intent, requirements, assumptions, and constraints from which an ontology can be discovered.

## Where ODPM Lives

Every framework has a moment where understanding becomes execution.

ODPM lives immediately before that moment.

| Framework | Execution Begins | ODPM Position |
|-----------|------------------|---------------|
| GitHub | Commit / Merge | Before the ontology becomes code |
| Scrum | Sprint | Before the ontology becomes work |
| PMBOK | Planning & Execution | Before the ontology becomes a plan |

ODPM is framework-agnostic because it sits upstream of execution, regardless of the framework being used.
