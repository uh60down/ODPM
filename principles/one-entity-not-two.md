# One Entity, Not Two

ODPM's first building block has one canonical name: Entity.

Not Concept.
Not Object.
Not Class.
Entity.

## Why Not Two Terms

Every time ODPM introduced two terms for nearly the same building block, confusion followed.

Concept. Entity. Object. Class.

People asked "what's the difference?" instead of learning the domain.

## Why Entity

Entity shifts the question toward the domain itself:

> What exists?

That is more direct than "what concepts exist?" and easier to teach than "what objects or classes exist?"

ODPM began with Concept because it emphasized abstraction.

Entity is now the better word because it emphasizes the domain.

The team is not first naming abstractions.

It is first discovering the things that make up the world it must act in.

## What This Avoids

ODPM does not need parallel terms for the same building block.

Instead of: Is this a Concept, Entity, Object, or Class?

Ask: What Entity exists in this domain?

Formal or technical synonyms can still be useful in their own contexts, but they map back to the same ODPM building block.

## The Building Blocks Have One Name Each

The same discipline applies to the five building blocks. Each has one canonical name — the plain-English one:

**Entity · Relationship · Action · State · Rule.**

Formal ontology and data modeling have their own words for these. Treat them as synonyms that map to the canonical set, not as a second vocabulary to maintain:

| ODPM (canonical) | Formal-ontology synonym |
|---|---|
| Entity | Entity / Class |
| Relationship | Relation / Association |
| Action | Transition / Event |
| State | State |
| Rule | Axiom / Invariant / Constraint |

ODPM keeps the domain-facing term deliberately: ontology is not philosophy, it is the team's shared model of the world.

Finer distinctions — an *understanding-unit*, an *agent*, a *constraint*, an *artifact* — are **roles an Entity can play**, not building blocks beside it. They live in the domain layer, as sub-kinds, never as rivals to the five.

## The Simplified Lifecycle

Entities anchor the ontology.

Relationships connect them.

Actions move them.

States describe their condition.

Rules protect the integrity of the domain.
